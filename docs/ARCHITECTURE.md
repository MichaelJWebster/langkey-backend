# LangKey Architecture Decisions

Lightweight ADR log. Newest first. Each entry: decision, rationale, revisit-when.

Scope is the whole of LangKey, not just this repo: decisions about the frontend
and about deployment live here too. It is kept in the backend repo because the
umbrella directory (`~/work/lang_app`) is not version-controlled, and symlinked
back to there so the familiar path still works.

## ADR-041 (2026-10-11) — A1 reading: authored passages, self-marked translation

*"I want to create subsections in Reading - The top one called \"A1 Reading and translation\" and the existing one with the novels and folktales in a section titled \"Reading for interest (not A1 based)\"."* The second half is a relabelling. The first is a new exercise: short Norwegian built from the deck, translated into English by the learner.

**No model on the request path.** The passages are static content, authored once and shipped like the deck — repo file, seed sync, hash gate. Generating them per request would put a model in the container (or a Cloudflare Workers AI call) on the critical path of a screen that must load, for content that is identical for every learner and every visit. It would also mean every obscenity and grammar gate runs live, against a deadline, with no chance for Michael to read what he is about to be shown. The pipeline instead is: author → deterministic gates → review → commit. The container already carries `data/`, so production needs nothing new.

**Marking is self-assessed.** Michael's call — *"we'll have to do self assessed"* — and it is also the right one. A free translation has too many correct answers to grade by string comparison, and the alternative is a model judging English prose, which is both a request-path dependency and a worse judge than the learner of whether they understood the Norwegian. What the app owes the learner is an easy judgement, not an automatic one: the reference translation beside their own, one question, three answers (`got` / `partly` / `missed`). The session percentage counts a partial as a half, because calling a near miss a failure would make the number useless as feedback.

**The reference is held back until Check.** It is sent to the client with the passage — this is practice, not an exam, and a round trip to reveal it would be a worse experience for no gain — but the UI does not show it until the learner commits. The answer box is kept with the mark, so the record of progress is the translations themselves and not just a tally.

**"Unfamiliar" is per learner, not per passage.** Michael, on trying the first batch: *"I notice there are words that I haven't seen appearing in the sentences, though they might be in the A1 vocabulary."* Being in the course is no help while reading if the deck has not got to the word yet, so a passage's glossary is the authored notes (`source: "new"` — outside the course) *plus* every deck word absent from this learner's `user_glossary` (`source: "unseen"`). Computed per request for the ten passages actually served, so the cost does not grow with the content file. Two defects surfaced the moment it ran against a real glossary, both of them in the merge rather than the idea:

- **Overlapping glosses.** `rett over gata` is a deck entry and so are `rett` and `over`, so a six-word clause drew three notes. Deduplicating by surface form was not enough; glosses now carry their span and a gloss contained inside a longer one is dropped. That also removes the duplicate when an authored note covers a phrase the deck happens to contain (`halv åtte` vs `halv`).
- **A verb glossed as a noun.** `dusjer` is `en dusj` plus a suffix *and* the present tense of `å dusje`. `_lemma_forms` generates inflections blindly, `forms.setdefault` gives the form to whichever item came first in the deck, and the noun won — so the gloss for a verb read "a shower". `FormIndex` gains `form_items`, keeping every candidate for a surface form; `forms` and `match()` are untouched, because the user glossary only needs to know a word was met. Anything that *shows* a translation joins the candidates (`a shower · to shower`) rather than picking one confidently. 211 of 7,993 generated forms are ambiguous this way.

**The glossary shows the inflected form, never the lemma.** *"with the words shown in the forms they're used in the Norwegian we want the user to translate."* `Hverdagen`, not `en hverdag`. A beginner cannot get from the dictionary form to the definite singular, and a glossary that makes them try is most of why glossaries go unread. The lemma is stored alongside and shown as a secondary note, for when it is useful rather than as the entry word.

**An exchange is laid out as a question and its answer.** Michael: *"It would be better if we formatted it like this: Question: Unnskyld, hvor er nærmeste bank? / Answer: Den ligger rett over gata, ved siden av apoteket."* Run together, an exchange reads as one person talking to themselves, and the shape of a question followed by its answer is half of what makes the second half guessable.

Which utterance is a question is **authored, not inferred**. Splitting on question marks would have worked on the two exchanges in the first batch and been wrong on `a1-023`, which is two question marks from a single speaker asking for directions. So a passage may carry `lines`: a list of `{role, no, en}` with roles `question`, `answer` or `line` (an unlabelled break). The English is split the same way, which also makes the self-assessment easier — the learner compares line against line rather than hunting through a paragraph.

`no_text`/`en_text` are **derived** from the lines when they are present rather than authored twice. Two copies of the same sentence drift, and the derived text is what the gates, the word count and the glossary run on, so a drift would mean gating text the learner never sees. A `JSON` column rather than a child table: lines are presentation, nothing references an individual one, and it avoids repeating the delete-then-insert dance the glosses needed. If per-line audio ever arrives they will want real rows, and that is the change to make then.

**Translating counts as reading on the dashboard rings.** Michael, with 28 passages behind him: *"I don't see a percentage for reading here - it's 0%?"* The skills breakdown had the tally by then, but the CEFR ring is a different endpoint, and its `reading_factor` was `sentences_read / 300` — sentences read **in the library**, which was still zero for him. So the ring said "no reading yet" while he had translated twenty-eight passages. A real gap, not a display problem.

Passages now contribute sentence-equivalents to the same factor, weighted by `MARK_CREDIT`, because a passage marked `missed` is not evidence of having read it — the same reasoning that makes the listening estimate discount vocabulary by the dictation mark rather than by attempts made. His 28 passages (24 got, 3 partly, 1 missed) come to 48.5 weighted sentences, a factor of 0.16, and the ring moved from 0% to 5%.

That number is deliberately not flattering. Reading is `vocab × reading_factor`, so it stays well under the 28% vocabulary ring until a few hundred sentences of text have gone through. At his current rate the full 200 passages would be ~346 sentence-equivalents and reading would saturate and track vocabulary, which is the right shape: translating the whole A1 set should make reading as strong as the words behind it, and not before.

**The score is a standing, not a session.** Michael, after a couple of dozen passages: *"I'm not seeing a percentage or score appear on the main page of the application, or in the reading exercises section."* The percentage existed only in the end-of-session summary and went away with it, so there was nothing to come back to. `Tally` is now computed per language and appears in three places: the exercise header, the A1 card in the Reading index, and the Reading subtitle on the dashboard.

Three decisions in it:

- **Quality and distance are separate numbers.** `score` is over the passages attempted, `attempted/total` is progress through the material. Rolling them together would make the score sink every time I add content — 91% over 28 would read as 13% against 200, punishing him for the batches.
- **Only the latest mark counts.** Going back and getting a passage right replaces the earlier miss rather than averaging with it, which is the behaviour that makes returning to a hard one worth doing.
- **A null score, not zero, before anything is marked.** 0% reads as "you scored nothing"; the UI shows "not started" instead.

A near miss is worth a half (`MARK_CREDIT`), the same rule the session summary already used, and the badge thresholds match the listening mark (ADR-040) so a percentage means the same thing wherever it appears. The library half of Reading gets no percentage at all — Michael was explicit that *"the scores are only for the sentences we created for exercises"*, and it is right: reading a novel is not an exercise with a right answer, and scoring it would invent a judgement nobody made. There is a test asserting the library card carries no `%`.

**Selection is not FSRS.** A passage has no recall interval worth modelling. The queue is: up to `REVIEW_SLOTS` (3) that went badly, then **the passages needing the fewest words explained**, then the rest. The cap is the point — without it a bad day becomes a wall of its own failures next session. Same reasoning as `REPEAT_LAPSE_CAP` in the repetition deck (ADR-038). A passage marked `got` is never retired, so the section cannot run dry.

**Passage rows are updated in place, not replaced** — `passage_attempts.passage_id` points at them, and this is the trap that took startup down when the deck grew (ADR-008's `_sync_examples`). Glosses and topics have no inbound references so they are rebuilt, but by `DELETE` then `INSERT` with an explicit `passage_id`: assigning the relationship makes the ORM insert the replacements before issuing the deletes, and the new rows collide with the old on `(passage_id, position)`. A passage dropped from the content file keeps its row, so the history of having worked through it stays readable.

**A gate bug worth recording.** The deck-coverage gate used `FormIndex.forms` to decide whether a word was known, and `FormIndex` routes every multi-word entry to `self.phrases` for substring matching instead — 548 of the 860 deck entries. It also drops `så` deliberately as too ambiguous to match. The gate was therefore blind to two thirds of the vocabulary and failed 6 of the first 25 passages on words Michael has (`nærmeste`, `ski`, `føle`, `bort`, `gått`). `FormIndex` is right for its own job; a coverage question needs a wider set, built from the tokens inside phrase entries too. Any coverage figure measured before this fix understates the truth.

**Difficulty is measured, not assumed.** Michael: *"favouring sentences where I've seen more words"*. The authored sequence was my guess at difficulty; the number of words a passage needs glossed for *this* learner is the real thing, and it is already computed. So the glossary is built for every passage before the sort rather than only for the ones served — pure CPU, a regex and some dict lookups each — and its length is the sort key, with the authored sequence surviving as the tie-break. The two cannot drift apart, because the number the sort uses is the number of hints the learner will see.

Worth noting what this orders by: the *count* of unfamiliar words, not their density. A thirty-word passage with one unknown word reads easily and a nine-word one with four does not, which the count gets right and a ratio would not. The effect on the first batch was large — `a1-025` (14 hints) went from last-by-authoring to last-by-measurement, which is the same place, but `a1-006` (0 hints) jumped from sixth to first and `a1-019` (7 hints) fell from nineteenth to near the end.

Revisit: the generation side is still manual. Haiku 4.5 through the Batch API costs well under a dollar for several hundred passages and would make regeneration cheap as the deck grows; the gates and the review step stay either way. The second-pass grammar check (NorMistral proposing a rewrite, reject on any disagreement) measured 5/6 faults caught on a nine-case probe, but its proposal diff currently counts a verbatim quote of the original as a change, so its false-alarm rate is not yet trustworthy.

## ADR-040 (2026-10-11) — æ ø å count, and every exercise shows its mark

Two asks in one breath, and the first came with its own precondition: *"I actually think we should count mistakes where we substitute a for å and the others - so long as we have fairly prominent selections of those special characters either on the phone or the computer."*

**The precondition first.** The characters already had buttons on both typed screens, but they were small (`px-3 py-1`, about 40×28) and sharing one non-wrapping flex row with the mistake light, Hint and Check — comfortably over a phone's width, so on the device where they are the *only* practical way to type æ ø å they were the first thing to be squashed. They now sit on their own row above the actions, 44px tall, splitting the width into three thumb-sized targets below `sm` and returning to normal size above it. The ⌥ shortcut hint is hidden on small screens, where it means nothing. Only then does the rule change.

**A missing diacritic is an ordinary spelling mistake.** It costs what any other wrong letter costs — similarity-based partial credit in dictation, a near miss rather than an exact answer in writing practice — and it can no longer produce a "correct" verdict. The folding helper survives, but only to *recognise* the shape of the mistake (`isDiacriticSlip`), never to forgive it: the feedback says "check æ ø å" so the learner knows which character, instead of a bare red mark.

**A slip does not reveal the spelling.** This is the subtle one. The first cut showed the correct word in amber, as the old near-miss did — but with the mistake now costing marks, showing the fix means he retypes it and the mistake costs nothing after all. A slipped word stays underscores like any other wrong word; only its colour and the light's wording differ. The skeleton reveals a word for getting it right, never for getting it nearly right (ADR-039).

**The short-word guard still applies, and should.** `hore` for `høre` comes out *wrong* rather than close, because the minimal-pair rule refuses near misses under five characters. That is the right answer here for a better reason than the rule was written for: `far` and `får` are different words, not one word spelt carelessly.

**An explicit mark on every exercise.** *"I'd like some explicit score to be created for these listening exercises, so we can get a percentage at the end of each exercise."* The per-word credit already existed but only surfaced when something went wrong — a correct answer said "✅ Correct!" and a percentage was never shown. Every result now carries the number in a badge, green at 100, amber from 60, red below; the verdict line beside it gives the reason rather than repeating the figure. The session summary leads with the average of those marks at display size, where it used to be a grey footnote under the right/total count.

Revisit: if the diacritic rule proves too harsh in practice, the lever is `isDiacriticSlip` — it already separates these from ordinary misspellings, so they could be scored on their own curve without going back to forgiving them.

## ADR-039 (2026-10-11) — The sentence's shape in dictation, and when a word is judged

Michael pressed Hint on a listening exercise believing he already had the whole phrase typed. He did not, and nothing on screen could have told him: the exercise showed his own input and nothing else, so the number of words still to come was invisible. His ask: *"I'd like to have an indication of what words are expected using underscores"* — `Hva heter du?` shown as `___ _____ __?`, each word filling in as it is typed correctly.

**One underscore per letter, punctuation left standing.** The punctuation is free information that costs nothing and anchors the shape, and the letter count is the point — it is what tells him whether the word he is reaching for is the short one or the long one.

**A word is judged only once it is complete**, which is the part worth recording, because the first design was wrong. Matching a prefix as the learner types looks helpful and is not: every learner is mid-word most of the time, so an early verdict means flashing an error at correct typing. Michael drew the line himself — *"there should be no indication of the correct characters being entered - just an indication when a correct word is complete or when a complete word is incorrect"* — and the implementation follows it literally. A word counts as complete when the learner has moved past it, which is exactly what the trailing space says. Nothing at all happens while the last word is being typed: no letters appearing, no colour, no sound.

**A wrong completed word stays hidden.** It turns the slot red but does not reveal the answer — guessing wrong must not be a way to see the word, or the skeleton becomes a free hint.

**The mistake light is derived, never stored.** It is recomputed from the input on every render, so correcting the word is what clears it; there is no error state that can go stale, and Hint clears it for free because Hint rewrites the answer to be right. Hinted words now carry a trailing space so they read as complete and show in the skeleton.

**The cue sounds on the edge only** — as a mistake appears, not once per keystroke for as long as it stands, and again only after the first one is fixed. It runs through `playback.ts`'s master gain like every other sound, so the volume control governs it (ADR-035) and it cannot become the one loud thing in the app.

Tolerance matches the checker exactly: a plain `a` for `å` shows the real spelling in amber and is never a mistake (ADR-019's rule, same `clean`/`fold` helpers).

Not extended to the typed recall cards in writing practice, though "in general" was the ask. There the expected answer is a translation, and a card accepts any wording the learner has vouched for with "that should have counted" (`user_answer_alternatives`), so a skeleton would show the shape of one accepted answer among several and quietly mark the rest as the wrong length. Revisit if the deck ever has a single canonical answer per card.

## ADR-038 (2026-10-10) — Ten vocabulary categories, many-to-many, and a repetition deck

Michael: *"the different topics we have in there, like Nature & Weather and Health & Body don't really have anything to do with the words being practised on in the sections."* He was right, and for a reason worth recording: `focus` only ordered the **introduction of new cards** (ADR-016). Due reviews came from one global FSRS queue, so picking "Nature & weather" with 203 words met produced a deck of mostly unrelated due cards under a nature heading. The label described how five of fifteen cards had been chosen.

Four changes, all under his request:

**The deck is a real A1 vocabulary.** 389 entries drawn from NTNU's *Norsk for universitet og høgskole* A1 word list, merged with the existing 471 to give **860 words**, all A1. Overlap with the existing deck was resolved by keeping the deck's own `no`/`en` wording, because the seed upsert matches on `(language_code, source_text, translation)` and changing either side would have orphaned a `user_cards` row and lost real progress. New words are appended rather than interleaved: the existing order is what Michael is partway through, and reshuffling it would change what he meets next for no benefit.

**Nineteen topics become ten categories, and an item may be in several.** The old `items.topic` column held one value, which forced arbitrary calls — `å betale` is money and it is shopping — and left categories too small to fill a deck (`communication` had five words). `item_categories` is a join table; `topic` is dropped. Michael asked for the overlap explicitly, and for progress to count a word learned in one category as learned in the other. That falls out of the schema: learning state lives on `user_cards.item_id`, so a word in two categories is the same word, met once, shown as met in both. The per-category totals therefore sum to more than the deck size (905 rows over 860 words) and `overall` counts distinct items — the screen states both rather than hiding the discrepancy.

**A category now restricts the deck instead of sorting it.** Both halves of the queue — due reviews and new cards — are filtered, so "Food & drink" means food and drink. A category that runs out is finished.

**The global queue gets its own section: Repetition.** Removing the spill-over from category decks would otherwise strand due reviews, and Michael asked for a larger repeating-practice section anyway: *"for repetition's sake, but also to ensure that I see the words I'm having more trouble with more frequently until my recognition improves."* `mode=repeat` draws 40 cards from everything met and introduces nothing new. Due cards lead, in due order, so FSRS still gets its reviews on time; the remaining room is sampled from the rest with weights for being due, unestablished, lapsed (capped at four, so one disaster does not dominate) and FSRS-difficult. It is sampled rather than sorted by need because taking the top N would show the same forty words every sitting — the opposite of repetition. The sampler (`app/sampling.py`) is shared with the speaking session, which wanted the same thing for the same reason (ADR-036).

Revisit: if ten categories still feel arbitrary once all 860 words are met, or if the repetition weights need tuning against his actual retention — the weights are constants at the top of `app/routes/reviews.py` precisely so they can be moved.

## ADR-037 (2026-10-10) — Speaking is its own section, with pronunciation and conversation under it

Recording moves out of the writing cards. It lived there because that is where the sentences were, not because it belonged: a learner reaching for pronunciation practice had to grade a translation first, and a learner writing translations was interrupted by a microphone under every example. Michael's call — *"I like the writing practice exercises, but I think the speech parts of them should be moved into a part of the speech section"* — and the section keeps the name the dashboard already uses, **Speaking**.

Speaking now opens on two subsections. **Pronunciation** is a lift and shift of what the review panel had: the slow clear reference (ADR-033), the speed chooser, the microphone, and the word-by-word feedback with its running tally (ADR-036). **Conversation** is a placeholder that says what it will be and why it comes second — it needs this section's recording and recognition plus a model to answer with (ADR-024). The speaking skill is no longer disabled on the dashboard (reversing part of ADR-023, whose condition was "until M3").

What the writing cards keep: the speak buttons. Hearing the word while reviewing is listening support, not speech practice, and removing it would make the cards worse. They play the default imitation rung, since the chooser went with the recording; if review ever wants its own speed control that is a separate decision rather than a leftover.

`GET /api/v1/speaking/practice` supplies the phrases: headwords and example sentences from items the learner has met (the same rule the listening exercises use), weighted ×4 toward phrases containing words the tally says are not landing, sampled without replacement so nothing repeats inside a session. Each phrase names the words it was chosen for, so the choice is visible rather than mysterious, and the session opens with the worst of the record above it. This is the first thing the `pronunciation_attempts` tally actually steers, which was the point of collecting it.

`SpeedChips` moved out of `ReviewSession` into its own module with the remembered-scale hook, because two screens now need it. Revisit: if the focus list fills with grammatical filler — `er` already appears — the fix is to weight by how much a word carries, not to raise the threshold, which would also hide real content words.

## ADR-036 (2026-10-06) — Pronunciation feedback in the record flow: word marks per take, a tally across them

Michael, after seeing the offline analysis: *"Would it be possible to provide that kind of analysis within the application as I'm using the record function?"* Yes, and the 2026-10-06 corpus says what shape it has to take. Across 56 takes, `klokka` failed in 68% of 22 attempts while fourteen other words never failed once — so **one take says almost nothing and the tally says a lot**. That asymmetry is the design.

What happens now: a take is saved, then transcribed, then lined up against the known target with `difflib.SequenceMatcher` over normalised words. Each target word comes back `said`, `slipped` (something close — `klokka` → `klokke`) or `missed`, and *what the model put there instead* travels with it, which is the whole value: a bag-of-words check only says a word is absent, where the alignment says what it became. Every word of every first transcription is appended to `pronunciation_attempts` (append-only, like `review_events` and `exercise_attempts`), and the response carries each word's running record. The UI marks the sentence inline, shows the raw transcript when it differs, and names a word as worth practising only once it has at least 4 attempts and a hit rate at or below 60%.

**A slip counts against the word.** The first cut counted `slipped` as success, and `klokka` — the single most informative finding in the corpus — vanished from the flagged list; it reappeared at 2/11 once only an exact match counted. `klokka` → `klokke` is not a forgivable variant, it is precisely the distinction the learner is not making. The written exercises forgive a diacritic slip (ADR-019) because a US keyboard is not a pronunciation; speech gets no such allowance.

**It is not a score, and says so on the page.** ADR-025 stands: a speech-to-text model repairs wobbly speech rather than reporting it, so no single transcript can grade anyone, and the panel reads "a guide, not a grade — the counts are what to trust". This is not the per-phoneme scoring of M3 step 4; it is word-level, it arrives from infrastructure that already existed, and it costs nothing extra to run. Step 4 remains the way to say *how* a sound was wrong rather than *that* a word did not land.

Mechanics. `POST /recordings/{id}/transcribe` keeps the first transcript on the recording, so asking twice is free and can never count an attempt twice — that idempotence is what makes the tally trustworthy. With no speech backend configured the route answers 503 and the client renders nothing: the feature is absent, never broken, and a take is always saved before any of this runs. Tonight's 56 takes were backfilled through the same path; the earlier corpus deliberately was not, because words lost to the capture bug (ADR-034) are not pronunciation data. Tests cover the alignment, the slip rule, the idempotence and the pattern threshold; `tests/conftest.py` now hides the developer's `.env` from the suite, which this work exposed — configuring a real backend had been quietly rewriting what the seam tests asserted.

Revisit: if the flagged list fills with words the model simply dislikes, raise `PATTERN_MIN_ATTEMPTS` before touching the rate; if it stays accurate, the same tally is the natural input to choosing what to drill.

## ADR-035 (2026-10-06) — One output stage: every clip levelled to a common loudness, behind a master volume

Playback went through a plain `<audio>` element per caller, at whatever level the clip happened to carry. That is wrong for the one thing the review panel exists to do. Measured on the existing corpus: Piper speech sits at about −10.5 dBFS, Michael's recordings at −20 to −28. Playing his take straight after the reference made it a third as loud, so the comparison he was being asked to make — *does mine sound like that?* — was dominated by a level difference rather than by pronunciation. His words: *"Could you try and match the volume of playback of my recordings with the references."*

`src/playback.ts` is now the single output stage. Each clip is measured once and scaled so its **speech** lands at −18 dBFS: 20 ms frames, averaging only those within 25 dB of the loudest, so the silence either side of a short sentence cannot set the level (otherwise the same voice with a longer run-up comes back louder). Gain is clamped to 0.2–8, which stops a near-silent take being amplified into noise. The measurement is cached per clip URL.

This has to be Web Audio: `HTMLAudioElement.volume` only attenuates, and his takes need **boosting**. Where Web Audio is missing, or `decodeAudioData` refuses the container — Safari cannot decode webm/opus — playback falls back to an element at master volume rather than failing. Decoding the whole clip before playing also removes a class of stutter the element had on headerless MediaRecorder blobs, which may be the other half of what he heard as "breaking" (ADR-034 fixed the measurable half).

A master volume rides on the same graph, persisted in `localStorage`, with a slider and mute in the app header so it is reachable from every screen — there was previously no volume control anywhere, and no single place one could have gone. **The slider is not the gain.** Levelling to −18 dBFS left the app quieter than Michael wants, so the midpoint reproduces what used to be the maximum and the top half is new headroom: `gain = (2 × position) ^ log2(3)`, which gives exactly 1.0 at 50% and 3.0 (+9.5 dB) at 100%, and the slider defaults to 50%. A `DynamicsCompressorNode` sits after the master gain as a safety limiter (threshold −2 dB, ratio 20, knee 0) because levelled peaks tripled would otherwise pass full scale; it engages only at the top of the slider. The element fallback stops at unity, since `volume` cannot exceed 1 — the top of the slider is reachable only through Web Audio. The storage key moved to `langkey.volume.v2`: under the old key a stored 1 meant unity and would now mean 3×, which is not a change to make silently on someone's next page load. `recordingObjectUrl` became `recordingBlob`, because levelling needs the samples rather than an object URL. `src/playback.test.ts` fixes the behaviour that matters: a −20 dBFS take and a −10 dBFS reference come out within a decibel of each other and on target, silence is left alone, and lead-in length does not change the result. Revisit: if any clip audibly pumps or clips after levelling, add a limiter rather than lowering the target; if Michael wants reference and voice at deliberately *different* levels for comparison, that becomes a second control rather than a change to the target.

## ADR-034 (2026-10-06) — Recording waits for the microphone, and asks for unprocessed audio

Michael: *"The recording on this page of my voice is constantly breaking, and corrupted."* Measured against the stored takes, it was: every take from 2026-10-06 is **832–957 ms shorter than the wall-clock recording time**, with the silence before his voice collapsed from 280–800 ms to 0–100 ms. The 5 October takes lose 18–66 ms. The opening word was not being captured, so playback started mid-syllable.

Cause: `getUserMedia` resolves while the audio device is still starting, and `MediaRecorder.start()` on that not-yet-live track records nothing until the first frames arrive. The UI then lit the record indicator immediately, so he was told to speak before anything was being captured. It surfaced now rather than earlier because ADR-033 put a long reference clip in front of every take — playing output and then opening input is exactly when the device reconfiguration costs most.

Two changes. `startRecording()` resolves only once the track delivers a non-zero sample (Web Audio analyser, polled on animation frames, 2.5 s cap so a silent device can never block recording), and the button shows "opening mic…" until then and "speak now" after. And the capture asks for raw audio — `echoCancellation`, `noiseSuppression` and `autoGainControl` all false. Those defaults are tuned for calls, not pronunciation: automatic gain is the best explanation for the one take that peaked at 1.03 while its neighbours sat at 0.33–0.88, and echo cancellation couples the input to whatever the page just played, which is now always the reference clip. The trade is that speaker bleed is no longer cancelled; measured bleed-through on the existing corpus was a cross-correlation of 0.05–0.12 with no spike, and he does not record while the reference plays, so this is a trade worth making for a signal that pronunciation scoring (ADR-025) will eventually have to align.

`armMs` rides on the `Take` so the delay is observable rather than guessed. Verification is the same measurement that found it: wall-clock duration minus decoded audio should return to under 100 ms on the next takes. `src/recording.test.ts` holds the first sample back and fails if `startRecording` resolves before it arrives, or if it stops asking for unprocessed audio. Revisit: if arming regularly costs more than a few hundred ms, keep the stream open across takes within a card rather than opening it per press.

## ADR-033 (2026-10-05) — The review panel is an imitation surface: one clear voice, at half the old pace

The clip a learner copies is not the clip they listen to, and the review panel serves the first. Until now it played `audio_url` — the example sentence's flashcard clip, whose speaker is hash-picked from an 11-voice pool at `length_scale` 1.6. Measured over seven sentences (voiced seconds only, 20 ms frames above −45 dBFS so trailing silence cannot flatter a slow clip): the pool voices run **5.26 syl/s**, the primary voice at the same scale 4.66, and Michael's own recorded attempts 3.96. The copy target was a third faster than he can speak, on a voice chosen by hash from a pool whose nvcc speakers mumble their first word (ADR-028) — six of his seven references came from nvcc, one of them `nvcc:4`, already on the pruning list. His own diagnosis, which the numbers confirm: *"They are too fast, and the voices vary too much for me to learn correct pronunciation. That is the section I think we need to use the best voice, and slow down at least 50%."*

Decision: `ExampleOut` and `ItemOut` gain `copy_audio_url` and `copy_speeds` — always `PRIMARY_VOICE`, on a ladder of five rungs. The whole review panel uses them: the example and headword play buttons, the `s` shortcut, and `RecordButton`'s reference. What you press play on is what you then record against, which was not true before. Two URLs rather than one setting, because the two jobs genuinely differ: to copy a sound you must first hear it in isolation, while to understand Norwegian you must cope with voices that do not accommodate you.

`PRONUNCIATION_SCALES = [4.0, 3.4, 2.8, 2.2, 1.6]`, default 3.4 → 2.63 syl/s, the first rung at or past half the old rate (measured on `talesyntese`: 1.6→4.66, 2.2→3.77, 2.8→3.02, 3.4→2.63, 4.0→2.19 syl/s). The whole ladder is offered rather than one chosen value, at Michael's request — the right pace is a judgement he makes, and a word met a hundred times does not need two seconds of vowel. The chosen rung is remembered in `localStorage` (as the dashboard focus chips are, ADR-016); `copy_audio_url` stays as the default rung so a client that ignores the chooser still works.

The imitation ladder reaches **slower than every rung of `DICTATION_SCALES`** (2,176 clips in all, generated 2026-10-05). It overlaps dictation at the fast end by arithmetic coincidence, not by design: an earlier version of this ADR pinned the imitation scale to a dictation value to reuse the clip, and that economy is given up on purpose, because dictation is comprehension practice and wants a pace you have to keep up with. The two ladders now move independently, and `tests/test_pronunciation_audio.py` fails if a later retune collapses them, if the two URLs merge, if the ladder stops being slowest-first (the UI labels rungs by position), or if the copy clip is ever drawn from the pool.

**Measured limit of this lever (2026-10-05).** Slowing further stops helping, and the numbers say why. On `Kan du hjelpe meg, vær så snill?`, going 3.4 → 4.0 adds 0.50 s of *voiced* time while the pauses between words *shrink*, 0.32 s → 0.24 s. Piper spends a higher `length_scale` stretching the sounds, not separating the words. Michael's complaint is that he cannot pick the individual sounds out, and a longer vowel does not make a consonant cluster any clearer — which is exactly why 3.4 already "appears a little stretched" to him. So 4.0 stays on the ladder as an option and is not somewhere to move the default. The lever that would actually help is word separation, i.e. the per-word clips below.

Consequence worth naming: the pool voices now play nowhere. Listening exercises already used `primary=True` at the dictation ladder, so the review panel was the pool's only remaining consumer. The clips are still generated and `audio_url` is still served, because ADR-018's argument for speaker variety has not been refuted — it simply has no surface right now. Deciding whether to delete the pool or give it a proper home (a "can you still follow a stranger?" drill) is deferred rather than settled by accident.

Not yet built, and now the favoured next step: per-word clips. Michael's suggestion was that a beginner may need each word enunciated separately before the sentence is useful at all; the pause measurement above turns that from a preference into the only remaining lever, since `length_scale` cannot buy word separation. It is a different artefact (one clip per distinct word, primary voice, around 2.2 where the voice still sounds natural) and a different UI (tap a word to hear it). The cheap half already exists, since most sentence words are deck headwords and already carry the full ladder. Revisit: after a few sessions against the chooser, with the question being which rung he actually settles on.

## ADR-032 (2026-10-05) — Speech runs as its own container in this repo, behind an interface built first

The conversation and pronunciation features (ADR-024, ADR-025) are **not** a third repo. ADR-001's two-repo split earned its keep because a Python API and a browser SPA have different toolchains and release rhythms; a speech service shares this repo's language, dependencies, Pydantic models and tests, so a third repo would buy two version streams to keep in step for a contract only one person consumes — the same cost ADR-026 refused for queues and monitoring. The existing split is already leaky in this direction: `wrangler.jsonc` lives in the *frontend* repo and builds the API image from `"image": "../langkey-backend/Dockerfile"`, so deployment already reaches across repos and a third would compound it.

It **is** a separate container, for two measured reasons. Resource profile: the API is comfortable on `basic` (¼ vCPU, 1 GiB), which is what production runs, while NB-Whisper needs ~1.5 GB and CPU bursts, so one shared container must be sized for the worst case — paying `standard-4` to serve flashcards. Image weight: ADR-024 bakes the weights into the image so a scale-to-zero cold start does not pull from Hugging Face, and shared, every API deploy would ship the model and every API cold start would pay for it. So this repo grows a second service with its own Dockerfile and entry point, sharing `pyproject.toml`, and `wrangler.jsonc` grows a second `containers` entry. One repo, one commit, separate images and instance types.

**The interface comes before the model.** There is no `Protocol` or ABC anywhere in `app/` today — ADR-001 required the exercise generator to sit behind a seam and it never got one, and ADR-027 was drafted claiming an audio/STT boundary existed when it did not. So the seam is work to do, not something to inherit, and it is the actual deliverable of M3 step 2: a `SpeechToText` protocol with one method, selected by configuration, so the transport can move from in-process on the M2 Max, to HTTP to a sibling container, to HTTP to GPU hosting, without a route changing. That is ADR-027's "keep the door open" applied to the one place it is about to matter.

The conversation LLM is a *client*, not a container of ours: Ollama locally, a hosted API in production (Workers AI, or Claude per ADR-021's finding that Claude handles archaic and rare vocabulary best). So the speech container holds NB-Whisper and Piper, and the character calls out. Revisit: if speech and API load ever want to scale together rather than apart, or if a GPU host makes the sibling-container step moot.

## ADR-031 (2026-10-05) — Standing decision: Norwegian-trained models, local or deployed

**Every model in the learner's path must be trained or fine-tuned for Norwegian, wherever it runs.** This is a requirement, not a preference to be traded away for convenience, and it holds equally for a model on the M2 Max, in a container, or behind someone else's API.

The evidence is why. NB-Whisper (National Library of Norway, Whisper retrained on 66,000 hours of Norwegian) scores WER 6.6 against plain large-v3's 10.4 on Fleurs, and 2.2 against 6.8 on NST — generic multilingual Whisper gives up roughly a third to two thirds of its accuracy on Bokmål (ADR-024). The same pattern showed up in translation (ADR-021): a generic dedicated MT engine was unusable on 1904 orthography. And in pronunciation (ADR-025), NOCASA 2025 was won by Norwegian-trained wav2vec2/XLS-R systems.

What this rules in and out. Workers AI `whisper-large-v3-turbo` at $0.0005/audio-minute stays documented as an *infrastructure* fallback only — reachable in an emergency, never the steady state, because it is generic Whisper. Commercial speech services that treat Bokmål as one locale among ninety are rejected for transcription. Azure Pronunciation Assessment is accepted for scoring because it is explicitly `nb-NO` and returns per-phoneme detail (ADR-025). Piper voices are already Norwegian. Where a Norwegian-trained option does not exist for a task, the honest answer is to defer the feature rather than ship a generic model and call it Norwegian.

The one deliberate exception is the conversation partner's text generation, where no Norwegian-specific instruct model is clearly better than a strong multilingual one; that choice is to be *measured* on Norwegian output before it is settled, and EuroLLM-9B-Instruct (European-focused, already downloaded) is the first candidate to benchmark against gemma3. Revisit: whenever a Norwegian-tuned model appears for a task currently served by a generic one — that is a reason to switch, not merely an option.

## ADR-030 (2026-10-05) — Reading library: categories derived from `kind`, English titles stored and hand-correctable

The reading library opens on broad categories rather than a flat list. A category *is* a text's `kind` (set by `prepare_text --kind`), grouped client-side in `categories.ts` from the listing the API already returns. There is deliberately no category table and no new endpoint: a new kind becomes a new category the moment the first text using it is imported, with a label derived from the kind string, so adding one costs an import and no code. `KNOWN` in that module only overrides labels and ordering for the kinds worth phrasing well; anything unfamiliar sorts to the end with a humanised label rather than being dropped. Revisit: if a text ever needs to appear in two categories, or if categories need their own ordering/description editable outside the code — then this wants a table.

Texts carry `title_en` beside `title`, nullable. It is translated at prepare time and checked by the ADR-029 gates, plus two rules that only make sense for titles: a reply more than three times the title's length is the model explaining itself, and a multi-word title handed back unchanged is the model giving up (a *one*-word identical reply is kept, because Victoria and Pan are titles in both languages). **Null is a first-class answer** — the reading list then shows the Norwegian title alone, which is what it would have shown anyway, so dropping a doubtful title costs nothing while storing a wrong one misleads the one decision a learner makes before reading.

Measured on the 27 texts in the library, machine-translated titles are much weaker than machine-translated prose: roughly half needed correcting, and the failures are semantic, so no gate can catch them (`Kveita` → "The Wife" for *the halibut*; `Havmannens sønn` → "The Mermaid's Son" for *the merman's*; `Tredokka` → "The Busybody" for *the wooden doll*). Four words carry no context, and unlike a sentence a title has no Norwegian beside it in the list to correct the impression. So `scripts/retitle.py` exists to set one by hand, and `import_text` keeps an existing `title_en` when the staging file has none — a hand correction lives only in the database and must survive a re-import.

Revisit: if a better translator (Claude, per ADR-021's `translator` column) makes title translation reliable enough to trust unreviewed.

## ADR-029 (2026-10-05) — Translation QA: deterministic gates, with repair wired only to gates measured near-perfect

Translations are checked by `scripts/translation_gates.py`: pure functions over the staging JSON, no model involved. Each gate is classified by who can fix what it finds. **TRANSLATION** means the Norwegian is sound and the English is wrong, so the translator can be asked again; **SOURCE** means the Norwegian itself is corrupt and retranslating cannot help, so the finding is reported and the fix goes upstream into extraction. `scripts/check_translation.py --repair` sends only the repairable findings back to the model with an instruction naming the specific fault.

The decision that matters is which gates get an instruction at all. **A gate with repair enabled rewrites what it flags, so a false positive does not waste a review — it replaces a correct translation with a worse one.** Measured on Mysterier (7228 sentences): the "Norwegian left in the English" check fires 28 times, but place names and deliberately kept loanwords land there too, and repairing those turned `ten øre` into `ten pence` and `«Skål!»` into `Cheers!`. It is report-only for that reason, and so is every other gate whose precision was not near 100%. Each gate carries its measurement in a `measured` field, and a test asserts the field is filled — the rule is enforced in code, not remembered.

A repair is accepted only when the gate that fired now passes **and** no gate that was passing has started failing, compared against the faults the sentence already had. Source-side faults are excluded from that comparison, or a page number fused into the Norwegian would make the sentence permanently unrepairable. Two attempts, then it is left for a human. Every accepted repair is recorded on the sentence as `repairs` (before/after), so a review can always see what the model first produced.

The acceptance rule caught its own hole in the first real run: the model answered one repair with the Norwegian sentence untouched, and no gate could see it — the word counts matched, and that sentence happens to contain no æ, ø or å. The echo check that already existed inside the translation loop became the `echoed_source` gate, with a four-English-word floor (without it, it fires 80 times on short lines that are their own translation: `Pause.`, `He-he-he.`).

`scripts/import_text.py` refuses a file with unresolved **fixable** findings and prints the `--repair` command; `--force` overrides. Source-side findings only warn. A gate that forces `--force` on every import teaches you to ignore it.

Revisit: when a second book's corpus disagrees with these measurements, or when a semantic check (does the English mean what the Norwegian means) is added — that needs a model and belongs beside these gates, not instead of them.

## ADR-028 (2026-10-04) — Audio QA: gate new clips on a swallowed opening word

Piper's multi-speaker `nvcc` voices under-articulate the first word of a sentence often enough to notice: measured over 766 example clips, **8.7% open too quietly**, with `nvcc:4` at **33.8%** (23 of 68) while **`talesyntese` and `nvcc:6` are at 0%**. The controlled case is 131 sentences that all begin "Jeg": median onset strength 83.8%, the strongest all `talesyntese` at 100%, the weakest all pool voices at 40–55%. The same word in the same prosodic position reaching half the level is a voice-quality difference, not prosody. The audio is **not** truncated — the word is mumbled — so leading silence and file length cannot detect it (the clip that prompted this has 360ms of lead-in).

Metric: the loudest 20ms within 200ms of speech onset, over the clip's own peak; flagged below 0.60. Two approaches were tried and rejected first — isolating the first word by its energy burst stops at the dip inside fricative-initial words like "smør" and "Jeg" and reports them as swallowed, and bridging those dips runs on through word boundaries, which in connected speech are frequently shorter, and measures the whole sentence. So no segmentation: a fixed window from onset. Headwords are excluded because many are an unstressed article or infinitive marker before a stressed word ("et hus", "å ville"), where a quiet opening is correct Norwegian.

`scripts/check_audio_onsets.py` is a **gate, not a repair**: it exits 1 on any weak clip not already in `data/audio_onset_issues.json`, so new content cannot quietly add more, and `--update` re-records the list. The 67 existing clips are recorded as a to-do; they are deliberately left alone rather than re-voiced, at the user's instruction, because re-picking voices changes the content hash and would regenerate most of the corpus. Workflow after content edits is now: `publish_deck` → `tts` run → `check_audio_onsets`. Revisit: fixing the recorded 67; `nvcc:4` is a candidate for removal from the pool (ADR-018 anticipated pruning poor speakers), though that reshuffles every hash-picked assignment.

## ADR-027 (2026-10-04) — Standing principle: design for many users, deploy for one

Architecture is designed on the assumption that LangKey may be commercialised and have to serve very many users; deployment is sized for the single-user prototype. The two are decided separately and argued separately, and every ADR should be clear about which layer it is talking about. **Deployment settings are cheap to change and may stay minimal**: container instance type and `max_instances`, scale-to-zero, one Neon branch, models running on the developer's Mac, a single region. **Code and schema must not assume one user**: no per-user state in process memory (any component must be able to run as more than one replica), no missing `user_id`, no request-path work that belongs in a queue, no local disk as a store of record, no N+1 query that only survives because one person is using the app. Audited 2026-10-04. Properties already held, to preserve: `user_id` on every user-owned table (indexed, with the right uniqueness constraints) and none on shared content tables; no per-user state in process memory (the only cache is `lru_cache` on immutable settings), so the API is already replica-safe at request level; no local disk as a store of record (content-addressed audio in R2/MinIO, everything else in Postgres); immutable append-only event logs (`review_events`, `exercise_attempts`); audio delivery behind a module seam (`app/audio.py`). **One door is currently closed:** `lifespan` in `app/main.py` runs Alembic migrations, `seed_data()` and `backfill_glossary()` on every container boot — correct at `max_instances: 1`, but two or more replicas would race on the same database. Trigger to fix before raising `max_instances`: move schema/seed work to a deploy step or guard it with a Postgres advisory lock. **Two seams do not exist yet and must be built open rather than retrofitted:** exercise generation is inline in `app/routes/exercises.py`, and there is no STT boundary at all, which is why speech must arrive as its own service rather than as code inside the FastAPI container (ADR-024, ADR-025). Deliberately *not* built until something demands them: queues, autoscaling, read replicas, sharding, multi-region, a CDN tier beyond what Workers already gives. The requirement is that the design permits them cheaply, not that they exist; where one is deferred, the ADR names the trigger and the cost rather than the mechanism. Revisit: at the first sign of a second concurrent user, or any commercialisation decision.

## ADR-026 (2026-10-04) — Agents belong in the content pipeline, never in the learner's request path

Agentic workflows (a model that plans, calls tools, checks its own work, and loops) are adopted only for offline content work behind the existing human review gate: filling the missing example sentences for items 151+, drafting answer alternatives so typed cards accept more wordings, and building the parked mock-Norskprøve exercises. The pattern copies ADR-021's text pipeline — pick the work, model drafts, automatic checks (known words only? can Piper say it?), staging folder, Michael approves, then the database. The gate is the design: everything before it can be wrong at no cost. Explicitly excluded: (a) anything the learner waits on — marking an answer, scheduling a card — which must stay fast and deterministic (ADR-019, ADR-022), and (b) the conversation partner, which is better modelled as a tightly constrained character with two or three tools than as an agent free to decide things. For a one-user app "agentic" should mean a script that calls a model and leaves something to review; queues, retries and monitoring are infrastructure with no payer here. Revisit: if content volume ever outgrows one person's review capacity.

## ADR-025 (2026-10-04) — Pronunciation assessment: not Kaldi; start bought, keep the option to self-host

Pronunciation scoring is a separate feature from conversation (ADR-024) with the opposite requirement: it must keep the learner's errors rather than repair them, so a speech-to-text model cannot do it — Whisper's value is precisely that it tidies wobbly speech into correct Norwegian. The pipeline is four steps: record → align the audio to the known target text → score each sound → explain. Kaldi, though the classic GOP (Goodness of Pronunciation) toolkit, is rejected: C++ with a steep build, a dying contributor base, no ready Norwegian acoustic model, and — decisively — NOCASA 2025 (Norwegian L2 pronunciation challenge) was won by wav2vec2/XLS-R CTC-GOP systems, not Kaldi. Chosen path: prove the feature with Azure Pronunciation Assessment (supports `nb-NO`, returns per-phoneme scores, pay-per-use), and only then decide whether to self-host a wav2vec2 CTC-GOP stack with NoFA (Språkbanken's Bokmål forced aligner) and the NST pronunciation lexicon. Always scoped to a known target sentence — never free speech. Expectation-setting: NOCASA's best system reached 36.37% UAR on four-way severity rating, so per-phoneme verdicts are a hint, not a grade; the UI must present them as "worth another go", and recording + A/B playback against the Piper reference carries much of the learning value on its own. **Confirmed empirically 2026-10-05, after one correction.** NB-Whisper transcribed seven Piper clips of known sentences 7/7 exactly, and the same seven sentences in Michael's own voice 1/7. The first write-up of that result claimed the codec, levels and SNR were ruled out; they were not. The Piper control was re-encoded by the same script that measured it, so it could never have exposed a fault in what MediaRecorder writes or in an individual stored take, and Michael then identified one of the seven (`Bananene er ikke modne ennå`) as audibly corrupted. Excluding it, the honest figure is **1/6 on audio he judges usable**. Re-running the control both ways (original WAVs and the opus re-encodes) gives identical transcripts, so the encoder introduces nothing; loudness does not explain the bad take either, since `piper7` peaks above full scale with 6 clipped samples and transcribes perfectly. The failures are not refusals or low-confidence output but confident, fluent, wrong Norwegian: `Kan du hjelpe meg, vær så snill?` came back as "Kom og hjelp meg med vaskene." A second experiment settles what kind of error this is: priming the decoder with the expected sentence (`prompt_ids`) changed nothing (still 1/6), and priming it with a *different* sentence never made it echo that sentence back (0/6). The model is not guessing or agreeing — the sounds it is being asked to find are genuinely not in the audio. That is exactly the repair behaviour this ADR predicted, and it rules the approach out for scoring as well as for feedback. Revisit: when there is a corpus of Michael's own recordings to measure against; if Azure's Norwegian scores feel wrong, self-hosting moves up rather than the feature being dropped.

## ADR-024 (2026-10-04) — Conversational speech: NB-Whisper, turn-by-turn, not on the Cloudflare container

Speech-to-text for the conversation feature uses NB-Whisper (National Library of Norway, Whisper retrained on 66,000 hours of Norwegian, Apache 2.0). The margin decides it: WER 6.6 vs plain Whisper large-v3's 10.4 on Fleurs, 2.2 vs 6.8 on NST. Alternatives are worse for Norwegian — plain Whisper gives up that margin, and commercial services treat Bokmål as an afterthought. Interaction is turn-by-turn (press, speak, release, transcribe) rather than streaming: simpler, and it matches how a learner actually composes a sentence. No GPU is required: utterances are seconds long, and faster-whisper's published CPU benchmark (small/int8, 8 threads) transcribes 13 minutes of audio in 1m42s using 1.5 GB RAM — several times faster than real time. A GPU buys latency on `large` and concurrency, neither of which a one-user app needs. Deployment, in build order: the M2 Max via Metal during development (free); then the existing Cloudflare container resized — `basic` (¼ vCPU, 1 GiB) is far too small, but the tier ladder runs to `standard-4` (4 vCPU, 12 GiB, 20 GB disk), which fits `small`/`medium` comfortably and `large` slowly, with the weights baked into the image (image cap = instance disk) so a scale-to-zero cold start does not pull from Hugging Face; Workers AI `whisper-large-v3-turbo` at $0.0005/audio-minute remains the zero-infrastructure fallback, but it is generic Whisper and gives up the Norwegian margin. Dedicated GPU hosting (EC2/ECS, or a scale-to-zero provider) is deferred until something demands it — an always-on g4dn.xlarge in Sydney is ~$500/month to serve one learner. ONNX and ggml/whisper.cpp builds exist; there is no official CTranslate2 conversion, so faster-whisper (the M3 plan of record) would need converting first. Revisit: when Workers AI or Cloudflare offers a Norwegian-tuned model, or when the local prototype justifies paid hosting.

## ADR-022 (2026-10-02) — Graded exercise marks and CEFR estimation

Listening attempts carry a `score` 0..1 (share of the sentence produced unaided; Levenshtein partial credit per misspelled word with a 50%-similarity floor; full reveal = 0). The mark drives dictation speed pacing (mean of last 12) and weighted sentence resampling (`_practice_need`: up to 4× likelihood for recently flubbed sentences, Efraimidis–Spirakis sampling). `/api/v1/progress/cefr` estimates per-skill CEFR position from an "effective vocabulary" read against Milton & Alexiou X-Lex sizes (A1≈500 … C2≈9000 lemmas); overall level = weakest practised skill; explicitly an estimate, not certification (Norskprøven is the official test). Pre-grading rows fall back to the old binary reading (hint-free correct = 1). Revisit: mock Norskprøve task sets (formats may be modelled from prove.hkdir.no samples; their content is copyrighted — original texts only).

## ADR-021 (2026-09-29) — Reading library: offline translation pipeline, sentence-per-row storage

Interleaved NO/EN reading texts come from an external pipeline, never the request path: `scripts/find_texts.py` (bokselskap.no catalogue / Gutenberg search) → `scripts/prepare_text.py` (fetch, class="para"-based extraction, sentence segmentation, local-LLM translation via Ollama — default gemma3:12b, paragraph-batched for context with numbered-line alignment, echo-detection retry for untranslated replies) → staging JSON in `data/texts_staging/` (gitignored; human review point) → `scripts/import_text.py` into Postgres. Storage is one row per sentence (`texts` / `text_sections` / `sentences` / `sentence_translations`): sentences immutable after import, translations versioned per translator with a partial unique index enforcing one current row, so gemma drafts can be upgraded (Claude/human) per sentence without re-import. `/api/v1/texts` serves 100-sentence pages; `user_reading_positions` (forward-only) is both resume point and cursor. Benchmarked first (Askeladden + modern Wikipedia passage): dedicated MT (OPUS-MT/NLLB-600M) unusable on 1904 orthography and drops facts on modern text; gemma3:12b good and literal; Claude best on rare/archaic vocabulary. Ollama models live on /Volumes/nvm_2tb. Revisit: per-sentence Piper audio (audio_key column ready) to link reading with listening; tap-a-word glossary; Claude repair pass for suspect sentences.

## ADR-020 (2026-09-28) — Adaptive listening difficulty

Three levers adapt to the learner: (1) dictation speed ladder — every example sentence has primary-voice clips at length_scale 2.0/1.6/1.25; the server suggests one from the last 12 dictation attempts (hint-free accuracy <55% → very slow, <80% → slow, else normal) and the UI offers override chips, with the used speed logged on each attempt; (2) sentence ease — dictation candidates are ranked by known-word coverage (glossary form-index matches ∩ items the user has met, over sentence length) and sampled from the easiest 60%; (3) exercise mix — dictation share of a session grows with total attempts (25% < 25 attempts, 40% < 75, then 60%). Piper note: durations are stochastic (noise_w), so scale verification needs repeated samples; an earlier generation mislabelled 1.5/1.8 clips a level fast, fixed by widening the ladder and regenerating.

Every attempt lands in `exercise_attempts` (immutable, like review_events) for future analytics/personalisation. Exercises draw only from items the user has met (recognition card reviewed). ## ADR-018 (2026-09-27) — Audio: 80% speed, multi-voice example sentences

All clips generated at Piper `length_scale=1.25` (≈80% speed, natural slow speech — not playback stretching). Headwords use the primary voice (talesyntese); each example sentence gets a stable hash-picked voice from an 11-voice pool (talesyntese + `no_NO-nvcc-medium`'s 10 speakers) so the learner hears varied speakers. Voice + scale are inside the content hash, so parameter changes regenerate cleanly; the generator prunes clips no longer referenced. Revisit: prune bad nvcc speakers from the pool if any sound poor; per-user speed setting.

## ADR-017 (2026-09-27) — Per-user glossary with example-sentence encounters

`user_glossary` records every deck item a user has met: the card's own word on first review ("card"), plus deck words recognised inside its example sentences ("example") via heuristic Norwegian morphology matching (`app/glossary.py`: suffix expansion + irregular-verb table + phrase substrings; misses acceptable — it's a reference, not the scheduler). Populated on first review of a card; backfilled at startup from review history. `/api/v1/glossary` reports each word's status (established / learning / seen-in-examples-only). Revisit: proper lemmatiser if matching quality matters later; tap-a-word inline glosses in the review UI.

## ADR-016 (2026-09-27) — Topics as new-card focus, not separate decks

Items carry a `topic` slug (19 areas; labels in `app/content.py`). A chosen focus steers only which NEW cards are introduced (`/reviews/queue?focus=...` — focused items first, merged across existing-unseen rows and uncarded items, spilling to frequency order when the topic runs out). Due reviews stay a single global FSRS queue — themed sub-decks would break scheduling. UI: dashboard focus chips (persisted in localStorage) + session-end "Keep going"/"Change focus". Richer themes (dialogues, lesson packs) belong to the exercises/content milestones, not the flashcard flow. Starter themed phrases added: meeting-people, directions, shopping (8 each).

**Superseded by ADR-038 (2026-10-10):** the single `topic` column is gone, a focus is now a hard filter over ten many-to-many categories, and the global due queue moved to its own repetition deck. The reasoning here is what went wrong — ordering new cards only was not visible to a learner reading the deck's heading.

## ADR-015 (2026-09-27) — Single learning step: no in-session repeats except Again

User found sessions too long (they shadow every phrase aloud, so each card takes real time). Learning steps cut from FSRS defaults (1m + 10m) to a single 1m step, relearning to a single 5m step: Good on a new card graduates immediately (returns in ~2–3 days); only Again cycles a card back within the sitting. Pedagogically sound: within-session repeats are massed practice, the weakest spacing; between-day gaps (untouched) carry the retention, and shadowing makes first exposures deep. Revisit: if new-word retention feels weak, restore a second step or add a next-day cap.

## ADR-014 (2026-09-27) — Piper audio pipeline with content-addressed clips

Audio clips live in MinIO keyed `audio/<lang>/<sha256(text)[:20]>.wav` — derived from the spoken text itself (derivation duplicated in `app/audio.py` and `docker/piper/generate_audio.py`; keep in sync). No DB bookkeeping: content edits get new audio on the next `docker compose --profile tts run --rm tts` (idempotent; reads the published deck Parquet, generates only missing clips; Norwegian voice no_NO-talesyntese-medium baked into the image). The API streams clips at `GET /api/v1/audio/{lang}/{hash}.wav`, unauthenticated (course content, no user data; Audio() elements can't send bearer tokens) with immutable cache headers. Frontend plays clip URLs and falls back to browser TTS per-URL on 404. Revisit: OGG/opus transcoding if storage/bandwidth matters; auth if audio ever becomes user-specific.

## ADR-013 (2026-09-27) — TTS: browser speech synthesis first, Piper-ready

The speak button uses the browser's `speechSynthesis` with an `nb-NO` voice (rate 0.9). Items and examples carry nullable `audio_key` columns; `speech.ts` prefers a pre-generated audio URL when present, so the Piper→MinIO pipeline (M2) slots in without UI changes. Revisit: when M2 lands, decide whether browser TTS remains the fallback for devices without audio yet.

## ADR-012 (2026-09-27) — Content pipeline: repo source → Parquet in MinIO → Postgres

Human-editable sources stay in-repo (`data/seed_deck_nb.json` + `data/extra_examples_nb.json`, merged by key `<no>||<en>`). `scripts/publish_deck.py` merges and publishes `decks/<lang>.parquet` to MinIO via DuckDB (boto3 for bucket/upload — no runtime DuckDB extension downloads). API startup loads the MinIO snapshot (falls back to local files in tests / before first publish) and syncs Postgres: items upserted by (language, source_text, translation) so user_cards FKs survive; examples replaced wholesale; a content hash in app_meta skips no-op syncs. Postgres remains the operational store — DuckDB/MinIO is the content/asset layer, per the M4 lakehouse direction. Revisit: consolidate the two source files when the M4 LLM content pipeline restructures authoring.

## ADR-011 (2026-09-26) — No daily new-card cap; batches per session

User decision: practice must be available whenever they log in. New cards arrive in batches of `NEW_CARDS_PER_SESSION` (10) per queue fetch, with no daily limit — each finished session unlocks another batch. Trade-off accepted: heavy binge days create larger future review load than a capped drip would (FSRS still spaces each card correctly). `new_available` in /progress reports total unseen candidates. Revisit: if review debt from binge sessions becomes unpleasant, add an optional soft cap or a "review-only" mode toggle.

## ADR-010 (2026-09-26) — Staged card directions

Every item first gets a recognition card (NO→EN). A production card (EN→NO) becomes eligible for introduction only after the item's recognition card graduates to FSRS Review state. Balances early speaking-oriented production practice against day-one review load. Revisit: if production cards feel redundant once speaking exercises (M3) exist.

## ADR-009 (2026-09-26) — FSRS via py-fsrs, state stored on user_cards

`user_cards` rows mirror py-fsrs Card fields (state/step/stability/difficulty/due); `app/scheduling.py` is the only bridge between the library and the DB. Default parameters, 90% retention; new-card batch size is a constant in scheduling.py (see ADR-011). `review_events` is an immutable append-only log — never update it; it feeds progress, streaks, and M4 analytics/personalisation. Revisit: parameter optimisation once real review history accumulates.

## ADR-008 (2026-09-26) — Seed deck is Claude-authored JSON in-repo

`data/seed_deck_nb.json`: 860 entries as of ADR-038 (447 at the time of writing), loaded idempotently at startup (only when the items table is empty for that language). Frequency rank = array order. Adding languages = adding a deck file + Language row. Revisit: M4 (LLM-generated content in-app), or if item edits need to propagate to an already-seeded DB (would need a proper content-sync command).

## ADR-007 (2026-09-26) — Postgres host port 5433 in dev

Compose maps Postgres to host port **5433** because another local container already uses 5432. Inside the compose network it remains 5432. Revisit: never, this is dev-only convenience.

Day-to-day data (users, items, reviews) is relational and transactional → Postgres. MinIO handles object storage (audio) from M2. DuckLake is added in M4 when analytical queries over review history exist; it layers over the same MinIO/S3 storage, so deferral is additive, not rework.

## ADR-001 (2026-09-26) — Two repos, versioned HTTP API between them

`langkey-backend` (deployable to a server) and `langkey-frontend` (browser SPA), coordinated from the `~/work/lang_app` umbrella directory (not a repo itself; holds ROADMAP.md, ARCHITECTURE.md, kickoff prompt).
